## 1. 模块目标 (Context)

本模块是 OpsPilot 平台的核心入口，供【甲方运维经理】使用。主要用于接收线下审批后的需求，在系统中创建"计划（Plan）"，并根据计划分类选择涉及的"台账范围"，最终生成唯一的 PlanID 并触发工作流的生成。

### 1.1 核心价值

- **需求入口**：承接线下审批通过的运维需求
- **台账关联**：与台账管理深度联动，记录系统生命周期事件
- **工作流触发**：自动生成标准化检查项
- **变更追溯**：完整的计划-台账双向追溯能力

### 4.2 Step 1: 填写基本信息

| 字段 | 组件类型 | 必填 | 说明 |
|-----|---------|------|------|
| 计划名称 | 输入框 | 是 | 计划标题，如"订单系统v2.0上线" |
| 计划分类 | 下拉单选 | 是 | 决定 Step 3 的范围选择界面 |
| 优先级 | 下拉单选 | 是 | P0/P1/P2/P3 |
| 执行时间 | 时间选择器 | 是 | 计划开始执行的时间 |
| 计划结束时间 | 时间选择器 | 否 | 预估完成时间 |
| 计划说明 | 富文本 | 否 | 补充说明 |

**【核心交互】**: 用户必须选择"计划分类(category)"，此选择将直接影响 Step 3 的范围选择界面。

### 4.4 Step 3: 选择涉及范围（核心动态交互）

前端根据 Step 1 中选择的 `category`，展示不同的组件交互：

| 计划分类 | 第一步接口调用 | 前端交互 | 台账操作 | 日志类型 |
|---------|---------------|---------|---------|---------|
| `new_system` (新系统上线) | 调用台账"**创建应用系统**"接口 | 弹出内嵌表单，填写新应用系统信息，可添加功能模块、云资源、账号 | 创建新台账 | `system_launch` |
| `new_feature` (新功能上线) | 调用台账"**选择应用系统**"接口 | 弹出台账列表单选已有系统，前端新增"**添加功能模块**"功能 | 新增功能模块 | `module_launch` |
| `func_change` (功能变更) | 调用台账"**选择应用系统**"接口 | 弹出台账列表选择应用系统，对应选择所涉及的**功能模块** | 更新功能模块 | `module_update` |
| `arch_change` (架构变更) | 调用台账"**选择应用系统**"接口 | 弹出台账列表多选应用系统，对应选择所涉及的**功能模块**，进行安全检查 | 更新应用系统+功能模块 | `system_upgrade` |
| `security_check` (安全检查) | 调用台账"**选择应用系统**"接口 | 面向应用系统层级，选择检查范围（全系统/指定范围） | 不修改台账，仅记录检查日志 | `security_check` |

## 5. 业务规则与强校验 (Business Rules)

### 5.1 PlanID 生成规则

系统在成功提交表单后，自动生成 `plan_id`。

- **格式**: `PLAN-{YYYYMMDD}-{当日三位流水号}`
- **示例**: `PLAN-20240322-001`
- **实现要求**: 后端需加锁或使用 Redis 原子递增，防止高并发下产生重复 PlanID

### 5.2 数据标签生成规则

自动生成 `tag` 字段。

- **格式**: `{PLAN-ID}-{分类简码}-{Unix时间戳}`
- **分类简码映射**:
  - `new_system` → `NEW`
  - `new_feature` → `FTR`
  - `func_change` → `FUN`
  - `arch_change` → `ARC`
  - `security_check` → `SEC`
- **示例**: `PLAN-20240322-001-NEW-1711171200`

### 5.3 时间强校验

- `planned_start_time` 必须严格大于服务器当前时间
- 前端实时校验，不满足条件时"下一步"按钮置灰
- 后端二次校验，防止绕过前端

### 5.4 审批材料必传

- 至少需要成功上传一个审批材料
- 文件大小 ≤ 20MB
- 未完成上传前，"下一步"按钮置灰不可点击

### 5.5 优先级联动规则

| 优先级 | 创建后状态 | 说明 |
|-------|-----------|------|
| P0 | 需二次确认 | 触发额外审批流程 |
| P1/P2/P3 | DRAFT | 直接进入草稿状态 |

### 5.6 计划状态管理与生命周期

#### 5.6.1 计划状态定义

| 状态 | 说明 | 与台账状态对应 |
|-----|------|---------------|
| `DRAFT` | 草稿状态，可编辑、可删除、可取消 | - |
| `IN_PROGRESS` | 执行中，计划已启动 | 台账状态保持 active |
| `COMPLETED` | 已完成，计划正常结束 | 台账状态保持 active |
| `CANCELLED` | 已取消，计划被取消 | 台账状态根据情况回滚或保持不变 |

#### 5.6.2 状态流转规则

```
┌─────────┐    启动计划     ┌─────────────┐    完成计划     ┌───────────┐
│  DRAFT  │ ─────────────> │ IN_PROGRESS │ ─────────────> │ COMPLETED │
│ (草稿)  │                │   (执行中)   │               │  (已完成)  │
└───┬─────┘                └──────┬──────┘               └───────────┘
    │                             │
    │ 取消计划                    │
    ▼                             │
┌───────────┐                     │
│ CANCELLED │<────────────────────┘
│  (已取消)  │      取消计划（异常）
└───────────┘
```

**重要规则**: 
- 计划一旦启动后（状态变为 `IN_PROGRESS`），**前端不允许取消计划**
- 计划状态与台账管理中的应用系统状态生命周期保持一致
- 创建计划时，台账状态为 `active`；计划取消时，根据业务规则决定是否回滚台账变更

#### 5.6.3 数据同步规则

| 操作场景 | 计划状态 | 台账状态 | 同步说明 |
|---------|---------|---------|---------|
| 创建计划（草稿） | DRAFT | - | 仅保存计划数据，不创建台账 |
| 启动计划 | IN_PROGRESS | active | 同步创建/更新台账，状态保持一致 |
| 计划完成 | COMPLETED | active | 台账保持 active 状态 |
| 计划取消（草稿阶段） | CANCELLED | - | 未创建台账，无需回滚 |
| 计划取消（执行中） | CANCELLED | active | 需根据业务规则评估是否回滚 |

#### 5.6.4 台账操作事务边界

#### 5.6.1 新系统上线 (new_system)

```
事务开始
  ├─ 创建应用系统台账 (inventory_applications)
  ├─ 创建功能模块 (inventory_function_modules) [可选]
  ├─ 创建云资源台账 (inventory_cloud_resources) [可选]
  ├─ 创建账号台账 (inventory_accounts) [可选]
  ├─ 创建生命周期日志 (inventory_lifecycle_logs)
  │     log_type: system_launch
  │     event_title: "【系统上线】{app_name} 正式上线"
  ├─ 创建计划记录 (plans)
  └─ 触发工作流生成
事务提交/回滚
```

#### 5.6.2 新功能上线 (new_feature)

```
事务开始
  ├─ 创建功能模块 (inventory_function_modules)
  │     status: online
  │     related_plan_id: 当前计划ID
  ├─ 创建生命周期日志 (inventory_lifecycle_logs)
  │     log_type: module_launch
  │     module_id: 新模块ID
  │     event_title: "【功能上线】{module_name} 正式上线"
  ├─ 更新应用系统台账 (inventory_applications)
  │     添加 related_plan_ids
  ├─ 创建计划记录 (plans)
  │     affected_modules: [{module_id, action: "create", ...}]
  └─ 触发工作流生成
事务提交/回滚
```

#### 5.6.3 功能变更 (func_change)

```
事务开始
  ├─ 更新功能模块 (inventory_function_modules)
  │     version: 新版本号
  │     last_change_time: 当前时间
  │     related_plan_id: 当前计划ID
  ├─ 创建生命周期日志 (inventory_lifecycle_logs)
  │     log_type: module_update
  │     before_data / after_data: 变更前后对比
  │     event_title: "【功能变更】{module_name} 更新至 {version}"
  ├─ 更新应用系统台账 (inventory_applications)
  │     添加 related_plan_ids
  ├─ 创建计划记录 (plans)
  │     affected_modules: [{module_id, action: "update", ...}]
  └─ 触发工作流生成
事务提交/回滚
```

### 5.7 幂等性保证

接口需支持幂等，通过前端生成的 `idempotency_key` 防止重复提交导致重复创建。

## 6. 异常处理 (Edge Cases)

| 异常场景 | 处理方案 |
|---------|---------|
| **并发流水号冲突** | 后端使用数据库唯一索引或 Redis 分布式锁，确保 PlanID 全局唯一 |
| **网络中断处理** | Step 3 接口超时，前端保留已填写的 Step 1 和 Step 2 数据，提示"加载台账失败，请重试" |
| **台账选择后失效** | 用户选择台账后，该台账被其他用户删除，提交时后端校验并提示"所选台账已失效，请重新选择" |
| **时间冲突检测** | 同一应用系统在同一时间段内存在多个执行中计划时，给予警告提示 |
| **事务回滚场景** | 创建过程中任一步骤失败，回滚所有数据变更，避免数据不一致 |
| **模块编码冲突** | 同一应用系统内模块编码必须唯一，后端校验并返回冲突提示 |

### 7.2 计划状态接口

| 方法 | 路径 | 说明 | 状态流转限制 |
|-----|------|------|-------------|
| POST | `/api/plans/:id/start` | 启动计划（DRAFT → IN_PROGRESS） | 仅 DRAFT 状态可启动 |
| POST | `/api/plans/:id/cancel` | 取消计划（DRAFT → CANCELLED） | **IN_PROGRESS 状态不允许取消** |
| POST | `/api/plans/:id/complete` | 标记计划完成（IN_PROGRESS → COMPLETED） | 仅 IN_PROGRESS 状态可完成 |

#### 取消计划限制说明

**前端限制**:
- 计划列表页：IN_PROGRESS 状态的计划，【取消】按钮置灰不可点击
- 计划详情页：IN_PROGRESS 状态的计划，隐藏【取消计划】操作按钮

**后端限制**:
```json
{
  "error": "CANNOT_CANCEL_IN_PROGRESS_PLAN",
  "message": "计划已启动，不允许取消",
  "current_status": "IN_PROGRESS"
}
```

**complete 接口说明**：

当计划标记为完成时，系统自动触发以下操作：
1. 更新 `actual_end_time` 为当前时间
2. 根据计划分类，执行相应的台账更新操作
3. 生成对应的生命周期日志
4. 更新关联台账的 `related_plan_ids`

## 9. 工作流模板集成

### 9.1 模板自动匹配机制

创建计划时，系统根据 `category` 自动匹配对应的 `template_type`，并预加载标准化的父工作项（检查项）配置：

```
┌─────────────────────────────────────────────────────────────┐
│                    计划创建工作流                           │
├─────────────────────────────────────────────────────────────┤
│  1. 用户选择计划分类(category)                               │
│           ↓                                                 │
│  2. 系统自动匹配 template_type                              │
│           ↓                                                 │
│  3. 根据分类确定台账操作方式                                │
│           ↓                                                 │
│  4. 从 Module_03 获取对应模板类型的标准检查项配置             │
│           ↓                                                 │
│  5. 用户填写台账/模块信息                                   │
│           ↓                                                 │
│  6. 创建 Plan 记录（包含 template_type 和 affected_modules）│
│           ↓                                                 │
│  7. 提交完成时执行台账操作并生成生命周期日志                  │
│           ↓                                                 │
│  8. 触发 Module_03 生成父工作项实例（检查项）               │
│           ↓                                                 │
│  9. 通知 Module_04 初始化工作流执行实例                      │
└─────────────────────────────────────────────────────────────┘
```

### 9.2 检查项生成时序

| 阶段 | 操作 | 涉及模块 |
|-----|------|---------|
| 计划创建 | 用户填写表单，选择分类 | Module_01 |
| 台账操作 | 根据分类执行对应的台账CRUD | Module_02 |
| 日志生成 | 生成生命周期日志 | Module_02 |
| 模板匹配 | 根据category自动匹配template_type | Module_01 |
| 检查项生成 | 基于模板类型生成父工作项（检查项） | Module_03 |
| 工作流初始化 | 创建工作项实例，等待乙方执行 | Module_04 |

### 9.3 计划分类与台账操作对照表

| 计划分类 | 模板类型 | 台账操作 | 生命周期日志 | 检查项重点 |
|---------|---------|---------|-------------|-----------|
| new_system | new_system | 创建应用系统+模块+资源+账号 | system_launch | 基础资源/台账/安全/监控 |
| new_feature | new_feature | 创建功能模块 | module_launch | 模块台账/接口/监控 |
| func_change | func_change | 更新功能模块 | module_update | 变更影响/回归测试 |
| arch_change | arch_change | 更新应用系统+资源 | system_upgrade | 架构评审/性能/安全 |
| security_check | security | 打标签或不操作 | - | 漏洞/基线/渗透/文件安全 |

## 10. 双向追溯设计

### 10.1 计划 → 台账追溯

#### 11.1.2 接口调用对照表

| 计划分类 | 第一步操作 | 调用台账接口 | 说明 |

| security_check | 选择应用系统 | `GET /api/v1/inventory/applications` | 面向应用系统层级查询 |

#### 11.1.3 功能模块数据同步

| 计划分类 | 功能模块操作 | 数据同步方式 |
|---------|-------------|-------------|
| new_system | 创建时添加功能模块 | 调用 `POST /api/v1/inventory/applications/:app_id/modules` 同步创建 |
| new_feature | 新增功能模块 | 调用 `POST /api/v1/inventory/applications/:app_id/modules` 同步创建 |
| func_change | 选择已有功能模块 | 调用 `GET /api/v1/inventory/applications/:app_id/modules` 实时查询 |
| arch_change | 选择已有功能模块 | 调用 `GET /api/v1/inventory/applications/:app_id/modules` 实时查询 |

#### 11.1.4 数据一致性保障

**实时同步策略**:
1. **创建计划时**: 在事务中同步完成台账创建/更新
2. **查询台账时**: 直接调用台账管理接口获取最新数据
3. **状态变更时**: 通过消息队列异步通知台账管理模块

**一致性检查机制**:
```json
{
  "sync_check": {

      "关联关系完整性"
    ],
    "last_sync_time": "2024-03-30T10:00:00Z"
  }
}
```

### 11.2 生命周期一致性

#### 11.2.1 计划状态与台账状态映射

| 计划状态 | 计划生命周期阶段 | 对应台账状态 | 说明 |
|---------|-----------------|-------------|------|
| DRAFT | 筹备阶段 | - | 未关联台账或台账为草稿 |
| IN_PROGRESS | 执行阶段 | active | 台账处于活跃状态 |
| COMPLETED | 完成阶段 | active | 台账保持活跃，记录变更历史 |
| CANCELLED | 取消阶段 | active/评估 | 根据业务规则评估是否回滚 |
