## 1. 产品概述

### 1.1 产品定位

**仿真运维经理**是一个面向运维专家和运维管理者的**计划驱动型准入管理系统**。系统帮助运维管理者在接到上线计划、变更计划等工作需求时，通过标准化的流程管理，确保所有交付物符合准入要求。

### 1.2 核心业务流程

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                         仿真运维经理 - 核心业务流程                          │
└─────────────────────────────────────────────────────────────────────────────┘

    接收工作需求                    制定管理计划                    执行核验
         │                              │                             │
         ▼                              ▼                             ▼
┌─────────────────┐           ┌─────────────────┐           ┌─────────────────┐
│ 运维管理者收到   │           │ 1. 创建计划      │           │ 6. 上传交付物   │
│ 上线/变更计划   │──────────▶│ 2. 拆解工作项   │──────────▶│ 7. 触发核验     │
│                 │           │ 3. 制定验收标准 │           │ 8. 得出核验结论 │
└─────────────────┘           │ 4. 排列工作流   │           └─────────────────┘
                              │ 5. 线下沟通要求 │
                              └─────────────────┘
                                       │
                                       ▼
                              ┌─────────────────┐
                              │ 各团队准备交付物 │
                              │ (线下执行)      │
                              └─────────────────┘
```

### 1.3 目标用户

| 用户角色 | 主要职责 | 使用场景 |
|---------|---------|---------|
| **运维管理者** | 计划制定、工作流编排、核验审批 | 创建计划、拆解工作项、制定验收标准、查看核验结果 |
| **运维专家** | 定义标准模板、配置验证规则 | 维护预置模板、配置脚本和AI分析规则 |
| **各业务团队** | 按工作项要求准备交付物 | 接收工作项要求、准备并提交交付物 |

### 1.4 核心价值

1. **计划驱动**：以计划为核心，所有工作围绕计划展开
2. **标准化拆解**：将复杂计划拆解为可执行的工作项清单
3. **灵活配置**：支持预置模板和自定义相结合
4. **多维度核验**：人工、脚本、AI三种核验方式
5. **全链路追踪**：从计划创建到核验完成的完整追溯

## 3. 详细业务流程

### 3.1 第一阶段：计划制定

#### 3.1.1 接收工作需求

**触发条件**：运维管理者收到上线计划或变更计划需求

**输入**：
- 上线/变更申请（线下审批通过）
- 涉及的应用系统清单
- 计划执行时间要求

#### 3.1.2 创建计划

**操作步骤**：
1. 进入计划管理模块
2. 点击"创建计划"
3. 填写计划基本信息：
   - 计划名称
   - 计划分类（标准上线/业务变更）
   - 优先级（P0-P3）
   - 执行时间
   - 涉及应用系统
4. 上传审批材料：
   - 会议纪要
   - 审批邮件
   - 其他截图

**输出**：计划创建成功，系统自动生成PlanID和数据标签

#### 3.1.3 拆解工作项

**操作步骤**：
1. 在计划详情页点击"拆解工作项"
2. 选择拆解方式：
   - **方式A：使用预置模板**
     - 选择系统预置的工作项模板（5大类）
     - 自动加载对应的子工作项
   - **方式B：自定义拆解**
     - 手动创建父工作项（大类）
     - 在父工作项下创建子工作项
3. 调整工作项顺序，形成工作流

**工作项层级结构**：

```
工作项拆解示例
│
├── 📊 服务对象台账收集（父工作项）
│   ├── 1.1 应用系统台账表（子工作项）
│   ├── 1.2 云服务开通台账表（子工作项）
│   └── 1.3 系统及软件账户台账表（子工作项）
│
├── 🏗️ 基础资源标准化交付（父工作项）
│   ├── 2.1 生产环境上线前系统基线配置（子工作项）
│   └── 2.2 生产环境软件标准化部署（子工作项）
│
├── 🛡️ 安全基线核验（父工作项）
│   └── 3.1 安全加固报告核验（子工作项）
│
├── 🔐 生产环境权限移交（父工作项）
│   └── 4.1 权限移交确认（子工作项）
│
└── 📈 监控告警配置确认（父工作项）
    └── 5.1 监控告警配置验证（子工作项）
```

### 3.2 第二阶段：验收标准制定

#### 3.2.1 为子工作项制定验收标准

**操作步骤**：
1. 选择需要制定验收标准的子工作项
2. 选择验收标准来源：
   - **预置模板**：从知识库选择标准模板
   - **文档导入**：导入MD/Word/Excel格式的基线要求
   - **手动输入**：自定义输入验收标准
3. 配置核验方式：
   - 人工核验
   - 脚本自动核验
   - AI智能分析
4. 定义交付物要求（格式、内容要求）

**验收标准组成**：

| 要素 | 说明 | 示例 |
|-----|------|------|
| 检查项 | 具体的检查内容 | "系统账户安全：禁止root远程登录" |
| 核验方式 | 如何验证 | 脚本自动检查SSH配置 |
| 通过标准 | 怎样算通过 | 配置文件PermitRootLogin=no |
| 交付物 | 需要提交的材料 | 脚本执行报告 |

#### 3.2.2 线下沟通与要求传达

**操作步骤**：
1. 系统自动生成《工作项清单与验收标准》文档
2. 运维管理者通过线下会议/邮件形式，将要求传达给各业务团队
3. 各团队明确工作项内容和验收标准

### 3.3 第三阶段：交付物准备与收集

#### 3.3.1 各团队准备交付物

**执行方**：各业务团队（线下执行）

**工作内容**：
- 按照工作项要求准备交付物
- 确保交付物符合验收标准
- 在计划执行时间前完成准备

#### 3.3.2 上传交付物

**操作步骤**：
1. 进入计划详情页
2. 找到对应的工作项
3. 点击"上传交付物"
4. 选择文件并上传（支持PDF、Word、Excel、图片等格式）
5. 填写交付物说明

**交付物状态流转**：

```
待上传 → 已上传 → 核验中 → 已通过
                    ↓
                 不通过/待改进
                    ↓
                 重新上传
```

### 3.4 第四阶段：核验执行

#### 3.4.1 触发核验

**触发条件**：交付物上传完成后，系统自动或手动触发核验

#### 3.4.2 执行核验

根据配置的核验方式，执行相应的核验操作：

**方式一：人工核验**
- 运维管理者查看交付物
- 对照验收标准进行检查
- 人工判断是否通过

**方式二：脚本自动核验**
- 系统自动执行预设脚本
- 脚本在目标服务器上运行
- 自动比对结果，生成报告

**方式三：AI智能分析**
- 系统自动解析交付物内容（如PDF报告）
- AI提取关键信息（如"通过"/"不通过"结论）
- 自动生成分析结果

#### 3.4.3 记录核验结论

**核验结论类型**：

| 结论 | 说明 | 后续操作 |
|-----|------|---------|
| **通过** | 交付物符合验收标准 | 标记完成，进入下一工作项 |
| **不通过** | 交付物不符合要求 | 退回，要求重新准备 |
| **待改进** | 基本符合，但有优化空间 | 记录问题，允许通过但需后续改进 |

### 3.5 第五阶段：计划完成

#### 3.5.1 计划状态更新

当所有工作项的核验结论都已确定后：
- 系统自动计算计划整体进度
- 更新计划状态为"已完成"
- 生成计划执行报告

#### 3.5.2 归档与复盘

- 所有交付物归档保存
- 核验结果汇总生成报告
- 支持后续审计和复盘分析

## 4. 功能模块详细设计

### 4.1 计划管理模块

#### 4.1.1 计划生命周期

```
草稿(DRAFT) → 待执行(PENDING) → 执行中(IN_PROGRESS) → 已完成(COMPLETED)
     │              │                    │                      ↑
     │              │                    │                      │
   创建中      到达执行时间         核验进行中              全部完成
   可编辑      或手动启动           进度实时更新            生成报告
```

#### 4.1.2 计划核心属性

| 属性类别 | 属性名 | 类型 | 必填 | 说明 |
|---------|-------|------|-----|------|
| 基本信息 | plan_id | string | 是 | 系统自动生成，如PLAN-20240322-001 |
| | name | string | 是 | 计划名称 |
| | category | enum | 是 | STANDARD(标准上线)/BUSINESS(业务变更) |
| | priority | enum | 是 | P0(紧急)/P1(高)/P2(中)/P3(低) |
| 时间管理 | planned_start_time | datetime | 是 | 计划执行时间 |
| | planned_end_time | datetime | 否 | 计划结束时间（预估） |
| | actual_start_time | datetime | 否 | 实际开始时间（自动记录） |
| | actual_end_time | datetime | 否 | 实际结束时间（自动记录） |
| 关联信息 | involved_systems | array | 是 | 涉及的应用系统列表 |
| | workflow_id | string | 是 | 关联的工作流ID |
| | tag | string | 是 | 系统自动生成的数据标签 |
| 状态信息 | status | enum | 是 | 计划状态 |
| | progress | int | 是 | 整体进度百分比（0-100） |

#### 4.1.3 计划仪表盘

**统计指标**：
- 计划总数
- 进行中计划数
- 待执行计划数
- 已完成计划数
- 已延期计划数

**可视化图表**：
- 近30天计划趋势图
- 分类占比饼图

- 完成率趋势图

### 4.3 核验执行模块

#### 4.3.1 核验方式对比

| 核验方式 | 适用场景 | 优点 | 缺点 |
|---------|---------|------|------|
| **人工核验** | 台账收集、文档审核 | 灵活、可处理复杂情况 | 效率低、主观性强 |
| **脚本核验** | 系统基线、配置检查 | 准确、可重复、自动化 | 需要目标服务器访问权限 |
| **AI分析** | 报告分析、文档解析 | 快速、可处理大量文本 | 需要训练、准确率依赖模型 |

         │

    ▼         ▼        ▼

## 5. 非功能性需求

### 5.1 性能需求

| 指标 | 目标值 | 说明 |
|-----|-------|------|
| 页面加载时间 | < 2秒 | 首屏加载完成 |
| API响应时间 | < 500ms | 95%的请求 |
| 文件上传速度 | > 2MB/s | 正常网络环境下 |
| 并发用户数 | > 100 | 同时在线操作 |
| 数据导出 | < 10秒 | 万级数据导出 |

### 5.2 安全需求

1. **认证授权**：JWT Token认证，支持Token刷新和过期
2. **权限控制**：RBAC权限模型，细粒度到按钮级别
3. **数据安全**：敏感数据加密存储，传输使用HTTPS
4. **文件安全**：文件类型白名单，病毒扫描，大小限制
5. **操作审计**：关键操作记录日志，支持审计追溯

### 5.3 可用性需求

1. **系统可用性**：99.5%以上
2. **数据备份**：每日自动备份，支持快速恢复
3. **故障恢复**：支持服务快速重启和数据恢复
4. **浏览器兼容**：支持Chrome、Firefox、Edge、Safari最新两个版本

### 5.4 扩展性需求

1. **模块化设计**：各业务模块独立，便于扩展
2. **插件机制**：支持自定义核验脚本和AI模型接入
3. **API开放**：提供标准API，支持第三方系统集成
4. **多租户支持**：架构上支持未来多租户扩展
